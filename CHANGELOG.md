# Changelog

## Unreleased

- Round 5 of the conformance vectors (vectors submodule pinned at 1490ec9): in a `/` or `@` report whose timestamp is not valid, when the seventh byte after the DTI is `z`, `/` or `h` and an uncompressed position follows the seven bytes (`@R30549z2831.07N/08142.92W_...`), the timestamp is garbled and the position is read after it, with `malformed-timestamp`; before, bytes such as `R30549z2831.0` could read as a compressed position straight after the DTI.
- Base-91 comment telemetry is the last valid block (R27, aprs-vectors#32, found in live traffic): in the text left after the elements lifted before it (a PHG, RNG or DFS at the start; in Mic-E the type code, the device suffix and a leading or later Mic-E altitude) the pairs of bars slide, each `|` closing one pair and opening the next, and the telemetry is the last pair that encloses 4 to 14 bytes, an even number, each `!` to `{`, as sent, whatever text and bars follow it; bars around anything else are text, with no diagnostic, and a block's bytes are base-91 whatever they look like (so in `x|!!!!|!W12!y|a b|` the telemetry is `!W12!y`). Before, only the text between the last two bars counted, so `|!a!'!#|| IGate PCBUnit 2 LoRa |144.190| BW10.4` had no telemetry and a `!DAO!` was lifted from inside the telemetry bytes. The `!DAO!` is then looked for outside the block, as before. Four observed Mic-E packets (`corpus/0845`, `1000`, `1232`, `1285`) gain the telemetry their sender wrote. The search looks at each bar once, so it stays linear on hostile input (the long-run timing test has bars as elements). The encoder is unchanged: data without telemetry whose comment holds a valid block is refused `text-reads-as-field` whatever bars follow it, and data with telemetry and a comment holding a block is written with the telemetry last, which the read-back confirms.
- A Mic-E locator's space is judged on the text after every lifted element is out, including a later altitude and base-91 telemetry after it: lenient no longer gives `missing-space-after-locator` there (telemetry an altitude splits is text, see below). The space is judged on the decoder's own result (the text left once the altitude, telemetry and `!DAO!` are lifted as for the data, with a `!DAO!` split by a lifted altitude not lifted), not on a separate trial removal: `IO91/G!W1"4e}2! hi` keeps `missing-space-after-locator`, and the locator's space separates it from the comment, so two spaces after the locator give the comment `x`. The vectors runner's tolerance check, for a case whose `strict` is rejected by a different code than its one tolerance, now needs a reading carrying that code as a warning; no case is skipped, and the runner asserts it ran on every case whose lenient diagnostics name exactly one tolerable code.
- Lifting an element never joins the text either side of it. Every element (base-91 telemetry, a `!DAO!`, PHG, RNG, DFS, a `/A=` altitude, a Mic-E altitude, a voice frequency and its fields, signpost or corridor braces, a weather field, the weather software type and unit) is recognised only where its bytes stand whole as sent, in every kind of comment, and nothing is read across the place an element was lifted from. The exception: The `/A=` lifted as the altitude may stand between a voice frequency and its first field, or between two of its fields, without cutting them off; nothing else may stand there, so a space before the `/A=` ends the fields, and a `/A=` inside any element splits it. A strict decoder no longer rejects by `mic-e-altitude-not-first`: it reads a later altitude as text. Text left that reads back as an element re-encodes `refused`, `text-reads-as-field`. Example: `PH|!!!!|G3330` is telemetry and the comment `PHG3330`, not a PHG.
- A voice frequency's tone, offset or range field is now read only when its space and its four bytes stand as one run: a `!DAO!`, base-91 telemetry, signpost braces or a late PHG/RNG/DFS lifted between the space and the value no longer joins them, and a field whose space stands before a `/A=` and whose value follows it is comment text.
- In Mic-E status text, the search for a later Mic-E altitude (three base-91 characters and `}`, when none is at the start) never uses the bytes of a `/A=` altitude that stands whole as sent, as it never uses a locator's bytes or a PHG's at the start: `x/A=000100}` has an altitude of 100 feet and the comment `x}`, lenient and strict alike, and `x/A=000100}y"4e}z` lifts `"4e}` with its warning. The lifting order is otherwise unchanged. The encoder writes a comment after a `/A=` straight on (`/A=000100x}`), no longer after a space.
- Hostile input: a long run of one candidate element no longer takes quadratic time. The late PHG/RNG/DFS search looked to the next lifted place for every candidate (200 KB of `PHG1`: about 2 s, new in this round) and the signpost and corridor brace search looked to the end of the text for every `{` (200 KB of `{`: about 4.6 s); each now looks no further than the element can be long. A test compares decoding time at 50 KB and 200 KB for each element in each kind of report.
- The read-back is one final check on every path that writes bytes, and it is the one place bytes come from (`readBack`, `readback.go`; the encoders return forms that only it turns into bytes). Before an encoder, builder or packet writer returns bytes it decodes them, leniently, under a well-formed header (`N0CALL>APZ001`; for Mic-E, the destination it computed), and compares the result with the data given: no `warning` or `error`; an `info` only on the form it belongs to (obsolete-format on positionless weather, raw weather, raw NMEA, a Maidenhead beacon and Mic-E Rev 0 telemetry; mic-e-missing-device-type on Mic-E status text with no type code; invalid-query and invalid-telemetry-metadata on a plain message); every field of the neutral form the same at every depth and in both directions, so a field the decode has and the data lacks refuses too; a number is never absent, and a NaN or an infinity never matches anything. Only these differences are allowed: a number a form holds in steps, rounded once to the step of the form written (compared with that exact rounded value), a value the form must carry (the default compression type, a Mic-E speed of 0, the fields an NMEA sentence determines), and empty text, an empty list, `null` and `false` as absent. A third-party packet's inner packet is compared the same way, with its warnings and errors as data: the decode must give exactly the ones the data gives (a multiset), infos not compared. If the first form does not match it writes the next equivalent one (a comment straight on, then after a `/`, then after a space) and if none does it refuses: with the code of the rule that names the fault where one does, `value-has-no-form` for an inner warning or error given that the written bytes do not carry, `text-reads-as-field` where free text reads back changed, else `does-not-read-back`. It runs before the 256-byte size check, on bytes over 256 too. It replaced the checks per report type and covers every type, third-party packets, user-defined data, test data, Agrelo and NMEA included.
- Third-party packets: every rule check that applies to top-level data now applies to the inner packets' data at every depth. An enumeration out of its type is `value-out-of-range` and a NaN or an infinity is `not-a-number` (before, a non-finite number in inner data read as absent, so bytes with no altitude were written for data that had one, and an out-of-range enumeration panicked). A decoded inner packet is written as received, so the defects it carries read back with it. Only the inner header of the third-party packet being written is judged, and read back by the third-party rules; a deeper level's header sits inside an information field and is written as received, so a decoded packet with a defective deeper header re-encodes identical. An inner packet written inside a third-party packet has its header read back by the third-party rules (a `ThirdPartySource` source such as `PY2SP_R-R` is written inside `}`, as in 1.2.0); the same packet written on its own as a line or frame is read back by the outer rules, so such a source is `invalid-address`.
- The header is read back too. A header as given is judged first, in every form, before any fault of the data: an address that is not one is `invalid-address`, and a path with an entry not marked used before one that is (it reads back used, in a line and in a frame alike, and no decoder gives one) is the new refusal `invalid-path` (`RefusalInvalidPath`), at `NewPacket`, a builder's `Build`, and `TNC2Line`, `TNC2`, `AX25` and `KISS`. A TNC2 line writes `*` on the last used entry only and an AX.25 frame sets the H bit of every used entry; H bits are read as a line's marks (an entry before one with its bit set is used, and several set bits are normal). Then the form's own limits, last: `ax25-cannot-carry` for a call over 6 characters or in lower case, an SSID a frame cannot hold, an empty address (a decoded packet's empty destination is written empty in a line, with the warning the packet holds, and refused in a frame) and more than 8 path entries; `tnc2-cannot-carry` for a CR or LF inside the information field of a line, which would end it there (one at the very end is carried), for a decoded packet and a hand-built one alike. A frame carries a CR or LF inside the field. `Station.Via` takes an entry ending in `*` as a used entry (`Via("WIDE1-1*", "N0CALL-1*", "WIDE2-1")`), as the neutral header form does, and `Packet.TNC2Line` gives the line with the reason it cannot be written.
- Refusal order: `not-encodable`; `invalid-address`, `invalid-path`, `invalid-third-party-header`; the data codes; `text-reads-as-field`, `does-not-read-back`; `information-field-too-long`; then `ax25-cannot-carry`, `tnc2-cannot-carry`, last, only when a form is written. A data fault or an over-long field beats a header only one form cannot carry, and `TNC2Line`, `AX25` and `KISS` still refuse such a header with sound data.
- Packet writers (`TNC2`, `TNC2Line`, `AX25`, `KISS`) pass `Information` through as held, whatever its length, and write a hand-changed `Packet` as it stands; only the header is checked, by reading it back, and a line refuses a CR or LF inside the information field as `tnc2-cannot-carry` (the line would end there), where it was written as it stood. `Packet.String` and `Station.String` are for display and are not writers: they never refuse, show the packet or station as held and are not read back (`Packet.String` used to be the line `TNC2` gives, with nothing for a refused packet).
- Dump tool: an inner third-party destination, path entry or source this package's types cannot hold is `invalid-third-party-header`, and an integer outside what its types hold (a voice offset at the least 32-bit integer, a telemetry value past 65535) is `value-out-of-range`, no longer `unsupported`. The recipe reader does the same for an ambiguity, a voice tone value and a voice offset (a whole offset that is not a multiple of 10 is `value-has-no-form`).
- A number given for a whole-unit or code field (a PHG or DFS digit, an Agrelo quality, a comment telemetry sequence or value, an area offset, a storm field, a DF bearing's fields) is never rounded: this package's types hold integers there, so the dump tool reports `value-out-of-range` (`not-a-number` for NaN or an infinity) for a record that gives a fraction.
- An empty message ID, or an empty directed-query target, is none: neutral data given `""` writes the message or query without it (it was refused, `invalid-message-id` and `invalid-addressee`); a reply-ack still needs a message ID and its `""` is a value. An ack's or reject's ID absent or empty is `invalid-message-id`. A builder still refuses an empty message ID (`MessageBuilder.MessageID("")`) as `invalid-message-id`, an empty destination (`To("")`) as `invalid-address`, and takes an empty comment as no text.
- A weather software type given without its unit, or a unit without its software type, is `missing-field` (it was `text-reads-as-field`). A control character in a weather extra field or unit is `invalid-character`, a rule check before the read-back.
- A Mic-E altitude is written first where the Encoding rule puts it: neutral data in the Mic-E bytes unless only a `/A=` holds it exactly, a builder's always in the Mic-E bytes, each with the comment straight on, after a `/` and after a space; then, if that was the Mic-E bytes, in a `/A=` that holds it exactly, so a comment that holds a `/A=` of its own gets the altitude in a `/A=` and the comment after it. A built packet's data holds the altitude as given, not rounded to the metre, and nothing is marked on it: the builder tells the encoder to start with the bytes by an argument, so `MicEBuilder.Data()` followed by `Station.Data(...).Build()` follows the neutral rule.
- The vectors' `pass_through_inner` key (a third-party packet's inner packet written on its own) is run by the vectors tests, and the dump tool's build mode gains `ax25` (the recipe written as a frame, hex, or `"refused"` with `ax25_refusal`) and gives an API view whose line cannot be written `"tnc2": "refused"` and `tnc2_refusal`.
- Second review (R28): an ambiguity of 0 is no ambiguity (nothing is written for it). A decoder takes the whole trailing run of CRs and LFs off with one `trailing-line-break` warning, and a packet writer carries the run; `tnc2-cannot-carry` is only for a CR or LF inside the field. Test data and user-defined data with a CR or LF inside are written as an information field alone and refused by a line as `tnc2-cannot-carry`; only data ending in one is `invalid-character`. A NaN or an infinity in any number of any data type is `not-a-number`, found by walking the data (so also the fields an NMEA sentence determines and every level of third-party data), unless a rule earlier in the refusal order names a fault first. An inner header out of order two levels down is `invalid-third-party-header` and a corridor width on an area that is not a line is `field-not-allowed`, not `does-not-read-back`. The dump tool gives the rule's code (`not-a-number`, `value-out-of-range`) for a non-finite raw rain counter and for legacy Mic-E telemetry values that are not bytes. A sweep test puts NaN, infinities, the largest and smallest finite numbers, -0 and fractions in every numeric field of every data type, at three levels of third-party nesting, and in every numeric builder argument: each call refuses or writes, never panics, and never writes a non-finite number.
- A packet's information field is read back under the destination it is written with, not the default one: a held packet whose Mic-E bytes are put under a destination that makes them a Mic-E report, a Mic-E report put under a destination that does not or under another Mic-E one (a different latitude digit, message bits, hemisphere, offset or SSID), and an inner third-party packet whose Mic-E data is under a destination other than the one it computes are refused `not-encodable` (the computed destination is never substituted), while inner Mic-E data under its own computed destination is written (it was refused).
- Speed against 1.2.0: encoding is slower, because every encode now decodes and compares what it wrote, and the comparison is built from the neutral form of both sides. A mixed set of seven reports (position, compressed position, object, message, status, telemetry, weather) takes about 17,500 to 21,000 ns now against about 7,500 ns in 1.2.0, so one encode goes from about 1.1 us to about 2.5 to 3 us (293 allocations against 120); decoding is unchanged (about 4,500 ns for seven lines). `BenchmarkEncodeMixed` and `BenchmarkDecodeMixed` measure it.
- Tests: for every report type a test makes the writers' bytes wrong in one place (a test-only seam) and checks the public call refuses them; others write data whose naive bytes read back as something else; and each clause of the comparison has a test that fails when the clause is taken out (a read-back that sees only a warning refuses, an unlisted info refuses, an info listed for one form is not accepted on another, a decode with a field the data lacks refuses, the inner warning and error multiset, the header diagnostics), plus one test for each defect the round's review found.

### Breaking changes for callers

- Comments that used to be read across a lifted element now keep that text: `/A=00!W12!0123` has a `!DAO!` and no altitude, `T100` after a frequency and a `!DAO!` or telemetry is comment text, and a Mic-E status text no longer gives telemetry, a PHG or an RNG made from the bytes either side of a later altitude. Re-encoding such a comment is `refused` (`text-reads-as-field`).
- A packet whose header cannot be carried is no longer written. A `Packet` with a path entry not marked used before one that is (`Path: {WIDE1-1, N0CALL-1*}`) gave the line `N0CALL>APZ001,WIDE1-1,N0CALL-1*:>hi`, which reads back with `WIDE1-1` used, and a frame with that H bit clear; now building it is `invalid-path`, and so is writing it with `TNC2Line`, `AX25` and `KISS` (`TNC2` returns nil). A decoded packet with an empty destination (`N0CALL>:>hi`) is still written back as a line, as it carries the `empty-destination` warning itself, and is `ax25-cannot-carry` as a frame (a frame has no empty address); one built by hand without that warning is `invalid-address`. A line whose information field has a CR or LF inside it is `tnc2-cannot-carry`. Check `TNC2Line`, or the error of `AX25`, where a packet may be one of these.
- A third-party packet is refused unless its inner packet reads back as the data it holds: an inner `Packet` whose `Data` is not what its `Information` says, or whose information field decodes with a warning or error its `Diagnostics` do not list (`Packet.Data` set by hand), was written as received and is now refused (`does-not-read-back`, `text-reads-as-field` where text changed, `value-has-no-form` for a warning or error given that the bytes do not carry, or the rule's own code, such as `not-a-number`, where the inner data breaks one). A packet decoded and re-encoded is unaffected: its own diagnostics are the ones it holds.
- `RefusalInvalidPath` is a new refusal code (the last in `AllRefusalCodes`; no value changes): a switch over `RefusalCode` needs a default case, as it always did.
- What 1.2.0 wrote is still written, except where it wrote a packet or line this version refuses (the header and line cases above): over the vectors' read-back shapes and the earlier generated sets (about 575,000 encode records and 465,000 build recipes, compared with 1.2.0's dump tool) no encode record that 1.2.0 wrote is refused now. What 1.2.0 refused and this version writes is an empty message ID or directed-query target, a Mic-E altitude in a `/A=` beside a comment that holds one, and a station path with an entry ending in `*` (the builder's `invalid-address`); a few records change their refusal code, and a few comments after a `/A=` or a signpost are written in the forms listed above.
- `Station.Via("WIDE1-1*")` is no longer an error.

## 1.2.0 (2026-11-14)

- `Device` now has a `String` method giving "vendor model" (for example `Yaesu FTM-400DR`), the same as the Python library's `str(packet.device)`. Printing a `Device` used to show the raw struct.
- The README's Mic-E and device snippet is now a tested example (`Example_micEDevice`); every other README snippet already was.
- Tests: when the `vectors` submodule is missing in a git clone, the vectors tests now fail with a one-line message to run `git submodule update --init`, instead of skipping and reporting ok. A copy fetched through the module proxy (no `.git`, and the module zip never holds the submodule) still skips, with the same message.
- Round 4 of the conformance vectors (vectors submodule pinned at 656d583). Licence: this library is MIT from this release; versions up to v1.1.0 were published under AGPL-3.0-or-later (the vectors are CC0).
- Round 4, run 5: the Mic-E builder writes free text after a voice frequency as ` /X` when ` X` at the end of the status text would read back as the device suffix, and not run on after the `MHz` (` X` stays plain before telemetry or a `!DAO!`); and the weather text of a positioned report ends where lifted base-91 telemetry or a `!DAO!` starts, wherever it sits, so a run-on value that reaches it is dropped (`out-of-range-value`) and the text after the element is comment text on its own, not joined to the run.
- A Mic-E locator followed by base-91 telemetry or a `!DAO!` and then a spaced comment (`` `IO91/G|!:&0'p| DG2MM ``) no longer gives `missing-space-after-locator`: the telemetry is lifted before the locator's space is looked for, so strict accepts it and the comment is `DG2MM`.
- An information field over 256 bytes is refused by every encoder and builder as `information-field-too-long` (new refusal code `RefusalInformationFieldTooLong`, last in the list; `too-long` now means only a field over its own limit); the size is the bytes the data's fields make, UTF-8 and number text included, and a third-party packet's limit is on the outermost field. The size is the last check, made on the bytes actually written after every other one (the read-back included): a record any other rule refuses gets that rule's code, and only an otherwise sound record over 256 bytes is `information-field-too-long` (a field over its own limit, such as message text over 67 characters, keeps `too-long` at its place in the order). Nothing is measured on a record that is refused. A decoded packet whose field is over 256 bytes decodes as before and re-encodes `refused`, `information-field-too-long`. `Packet.TNC2`, `AX25` and `KISS` write out a packet the program already holds: they are not encoders and write its information field as it stands, with no size check (their docs say so). The README no longer says the encoder has no size limit.
- A byte below 0x20 or the byte 0x7F in text (a comment, status text, a message, bulletin or NWS bulletin text, telemetry names, units and project title, capability values, the free text a weather report or an NMEA sentence leaves, a Maidenhead beacon's comment) gives one `control-character-in-text` warning (new code, tolerable), judged after the text's structure and encoding; `aprs.Strict` rejects it. TAB, and a CR or LF inside the text, count. User-defined, raw weather, test and undecoded data, Mic-E fixed bytes and Rev 0 telemetry, object and item names, capability tokens, addressees, headers and NMEA sentences keep their own rules. The encoder and builders refuse such text as `invalid-character` (it was only CR and LF); a Mic-E status text starting with 0x1D is refused instead of being written after a `/`.
- New code `CodeImplementationLimit` (`implementation-limit`) so the codes match the vectors. This library has no fixed capacity and never gives it.
- A fixed-width weather field whose digits run on by two or more, followed by the end of the information field or by a defined field still to be read, is `out-of-range-value`: the value is dropped and the fields carry on after the run (`t2147483647r000` has a rain of 0 and no temperature). The dropped value counts as present for `incomplete-weather`. Anything else after the run keeps the 1.1.0 rule.
- Builder defaults, written down: a builder never reads the clock; an object or positionless weather report with no timestamp is `missing-field`; a position, object, item or Mic-E report with no symbol is `invalid-symbol` (it was `missing-field`); a weather report's symbol is `/_`. A builder's refusal for a symbol or timestamp left out is named at its place in the order of refusals, not first: an object with a name too long and no symbol is `invalid-name`, and a positionless weather report with a humidity of 0 and no timestamp is `value-has-no-form`. A Mic-E altitude outside the Mic-E bytes' range is ranked the same way, so `not-a-number` elsewhere in the report wins over its `value-out-of-range`. The other defaults (not messaging, Mic-E off duty and type code `'`, telemetry bits `00000000`, no path, destination `APZ001`, no ambiguity, no compression) are unchanged.
- A Mic-E altitude goes in the Mic-E altitude bytes, rounded once to the nearest metre from the value given in either unit (1000 feet is 305 m); outside -10000 to 743570 m it is `value-out-of-range`, not moved to a `/A=`. `MicEBuilder.AltitudeFeet` no longer writes a `/A=`. The encoder, given neutral data, writes a `/A=` only for a whole number of feet within six digits that the Mic-E bytes do not hold exactly (1000 feet is `/A=001000`, -50000 feet is `/A=-50000`), and otherwise the Mic-E bytes (100.5 feet is 31 m); an altitude read from a `/A=` is still written back as one.
- Neutral telemetry data with no sequence is `missing-field` (it was `malformed`), and a positionless weather report with no timestamp is `missing-field` (it was `invalid-timestamp`).
- A Mic-E altitude with no type code before it, that no `/A=` holds exactly (not a whole number of feet, or beyond six digits) and whose first Mic-E byte would read as a type code, is `value-has-no-form`, not `text-reads-as-field`.
- A run-on weather value followed by its own field's letter (`t05700t057`) keeps the 1.1.0 reading: the run's own field counts as read, so it does not qualify.
- The vectors test runner runs the new `build` cases (builder recipes) through the real builders, with the same code as the dump tool's build mode (`internal/recipe`).
- The dump tool passes only the keys a recipe gives and never fills one in: a telemetry recipe with no sequence is `refused`, `missing-field` (the dump tool used to build it with sequence 0).
- The README says 1.2 and 33 tolerable defects.
- The dump tool, build mode: a recipe giving a quantity in two units whose one-unit builds are refused only for the 256-byte size is `value-given-twice`; the size ranks after it.
- The dump tool no longer reports `unsupported` for an input whose value alone decides a refusal code: a symbol that is not a table and a code (`invalid-symbol`), a third-party path entry that is not an address (`invalid-third-party-header`), undecoded inner data (`not-encodable`), an Agrelo bearing or quality out of range (`value-out-of-range`, `not-a-number` for NaN or an infinity), a bulletin id that is not one character (`invalid-addressee`) and a telemetry sequence outside 0-65535 (`value-out-of-range`) or not a number. The input is replaced by a valid stand-in, the record is encoded or built, and the first code in the Refusal reasons order among that result and the input's own is reported, with `"via": "tool"` when the tool's reader made it. The vectors test runner reads encode data the same way, and the `encode/nested-third-party-ending-in-undecoded-data` case, which it used to skip, now runs.
- Agrelo bearing rounding (12.5 is 013, 360.4 is 360, 360.5 is refused) is done by the dump tool's reader on neutral data, not by the library: `AgreloDF.BearingDegrees` is a whole number of degrees, and a caller of the Go API rounds its own value.
- Storm data's fields are digits: a field of dots or spaces is no longer storm data (the text stays in the comment), a whole gale radius that is not digits ends the storm data, and an encoder refuses storm data missing a required field as `missing-field` instead of writing dots. `Storm` fields that are nil in decoded data can no longer occur for the required ones.
- A telemetry sequence of `MIC` followed by more characters given to an encoder is `malformed` (it was `text-reads-as-field`).
- A run-on weather value in a positioned report is judged against the end of the weather text: a trailing base-91 telemetry block or `!DAO!` (lifted first) is not part of it, so `t2147483647!W12!` drops the run with `out-of-range-value` and reads the `!DAO!`.
- `Data()` on the object, item, position, Mic-E and weather builders refuses a symbol or timestamp left out with the same code `Build()` gives (`invalid-symbol`, `missing-field`), as in 1.1.0; it briefly returned the data with no error in this round.
- The dump tool marks every refusal it makes on the library's behalf `"via": "tool"` (a quantity in two units, a telemetry recipe with no sequence, the stand-ins), supplies no default the library lacks, and builds a recipe with no `station` from N0CALL as the vectors say.

### Breaking changes for callers

- An encoder or builder refuses an information field over 256 bytes (`information-field-too-long`); writing out an existing packet with `TNC2`, `AX25` or `KISS` is not encoding and does not.
- Text with a control character is refused (`invalid-character`), and a decoder gives `control-character-in-text`, so `aprs.Strict` now rejects such packets.
- A run-on weather value before a defined field or the end of the field is dropped with `out-of-range-value`, where it used to be read at its own width with the rest as text.
- A position, object, item or Mic-E report built with no symbol is refused as `invalid-symbol` (it was `missing-field`), and an object or positionless weather report built with no timestamp as `missing-field`, each ranked at its place in the order of refusals.
- A positionless `WeatherReport` with no timestamp, and a `Telemetry` with no sequence, are `missing-field` (they were `invalid-timestamp` and `malformed`).
- A Mic-E report's altitude given in feet goes in the Mic-E altitude bytes, rounded to the metre, instead of a `/A=` in the status text.
- Neutral Mic-E data of -50000 feet is written as `/A=-50000` instead of refused; neutral Mic-E altitudes that are neither whole feet nor whole metres go in the Mic-E bytes (they were a `/A=`).
- New `Code` values `CodeControlCharacterInText` (inserted in the middle of the list, so every `Code` after it moves up one) and `CodeImplementationLimit` (appended at the end), and a new `RefusalCode`, `RefusalInformationFieldTooLong` (appended at the end): do not store a `Code` or `RefusalCode` as a number.
- The 256-byte size refusal is `information-field-too-long`, not `too-long`: code that matched `RefusalTooLong` for an oversize field must match the new code too.
- Storm data with a dotted or blank field is comment text now, and an encoder refuses a `Storm` with a nil required field (`missing-field`) instead of writing dots.
- A telemetry sequence beginning `MIC` and longer than `MIC` is refused as `malformed`.

## 1.1.0 (2026-11-14)

Round 3 of the conformance vectors (pinned at 10d4e25).

### Behaviour changes

- A lower-case grid locator is refused as `malformed` by `Encode` in a status, a Mic-E report and a Maidenhead beacon (it used to be written in upper case). `StatusBuilder.Locator` still writes it in upper case.
- An AX.25 address holding anything but upper-case letters and digits (punctuation, a space before the last character, a control character) is now `invalid-address`; a lower-case letter is still tolerated.
- The decoder reads at most four levels of third-party header, and the encoder refuses a chain nested deeper with `invalid-third-party-header`.
- More than five analog values in a telemetry report or in comment telemetry are `too-long`.

### Changes

- Third-party packets nest at most four deep: a fifth `}` makes the packet holding it `unrecognized` with `error:invalid-third-party`.
- A call of spaces only in an AX.25 frame is an empty source (`invalid-address`), destination (`empty-destination`) or digipeater (`empty-path-entry`, dropped from the path).
- An ambiguous position is cut to its box, not rounded, in uncompressed and Mic-E reports, so a value just under 90 or 180 degrees is written.
- An ambiguous position whose box would be centred past 90 degrees latitude or 180 degrees longitude is `value-has-no-form`.
- A compressed wind direction is judged in whole degrees before it is rounded to the 4-degree step: 360.5 and -0.5 are `value-out-of-range`.
- A field wanted twice (a PHG, RNG or DFS that loses the one data extension, or a course, speed or wind beside a range or a GGA altitude in the cs bytes) keeps its own range checks, so its refusal can outrank `extension-conflict`.
- A course or speed beside a compressed weather report's wind keeps its own checks (a course of 0 is `value-has-no-form`).
- Base-91 telemetry on a weather report is `field-not-allowed` and its own checks do not run.
- A reply-ack that is wrong on its own is `invalid-message-id` even with no message ID.
- Builders refuse in the encoder's order: out of range comes before the ambiguity edge's `value-has-no-form`, and the telemetry builder passes extra analog values to the encoder.
- A compressed GGA weather report with an altitude of 1 foot or less is written, the nearest cs value alone, and reads back rounded, as for any altitude its cs bytes cannot hold exactly.
- An NMEA field or a compressed coordinate that is not a number is `not-a-number`, named before an invalid sentence, a comment with a line break, or the other coordinate being out of range.
- A speed, course or other whole-number field given as NaN or an infinity is `not-a-number`, not `value-out-of-range`.
- The dump tool reads the `NaN`, `Infinity` and `-Infinity` tokens the generator writes, and ranks a recipe that gives a quantity in two units: it builds once with each unit and reports the first code among those results and `value-given-twice`, never `unsupported`. A recipe ambiguity that is not a finite number is ranked as `not-a-number`.
- The dump tool's reader names undecoded inner data in a third-party packet before a header fault, and reads an absent positioned symbol as an empty one (`invalid-symbol`).

## 1.0.1 (2026-11-13)

First Go release. It matches the conformance vectors at 1.0.1: every case passes, and it writes the same bytes as the other five implementations (C#, Rust, Python, TypeScript and C) over the vectors' cases and over differential runs of generated data, builder recipes and fuzzed packets.

- Decoding from TNC2 / APRS-IS text, AX.25 frames and KISS frames, every APRS 1.2 data type, with lenient, strict or per-code options. The zero `ParseOptions` is `Lenient`.
- Encoding and the station builder, with read-back checks and the 26 shared refusal codes (`EncodeError.Code()`). `Encode` and `NewPacket` take a data value or a pointer to one.
- TNC2, AX.25 and KISS output, device identification from the APRS device identification database, and named symbols.
- `cmd/aprs-diffdump`, the dump tool for the vectors' `tools/compare.py`.

The version starts at 1.0.1 to share its major and minor version with the vectors and the other implementations.
